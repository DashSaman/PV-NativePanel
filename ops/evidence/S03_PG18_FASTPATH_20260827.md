# S03 PostgreSQL 18 pgcrypto fastpath

Target: `testAmir5-3`
Stage: `S03-DATABASE`

Root cause reproduced in GitHub Actions with PostgreSQL 18.6:

- `pvnaive.has_valid_context()` and `pvnaive.set_request_context()` are `SECURITY DEFINER` functions with a restricted search path.
- Their unqualified `hmac(...)` call could not be resolved at runtime because `pgcrypto` is installed in `public` while `public` is intentionally excluded from the security-definer search path.
- Moving the trusted extension after installation was rejected because pgcrypto member functions are not owned by `pvnaive_owner`.

Canonical pre-first-deployment fix:

1. Keep schema version `1`; S03 has never reached `PASSED` and no production PVNaive schema exists.
2. Keep pgcrypto in its installed schema.
3. Call the exact extension function as `public.hmac(...)` from both security-definer context functions.
4. Revoke `CREATE` on schema `public` from `PUBLIC` as defense in depth.
5. Keep the security-definer search path restricted; do not add `public` to it.
6. Recompute `db/migrations/SHA256SUMS` from the patched initial migration.
7. The temporary schema-v2 migration experiment was removed and is not deployable.

Required gate: PostgreSQL 18 CI must pass migration, RLS, health, encrypted backup, restore and rollback before target-host execution.
